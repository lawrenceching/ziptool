# 打包方案审核 UI 规格(P0 契约)

> 定位: P0 设计契约, 供 P3 壳层命令与 P4 UI 实现共同遵守。
> **已拍板**: 审核只读 / 默认开启 100m + 2g / 摘要 + 表格分组。
> 实现进度: P1/P2 core 已完成(2026-10, `Entry.entry_count` + `packaging.rs`); P3 壳层已完成; P4 策略行/摘要/策略列/表格分组与 P5 包级状态已完成(方案直接在表格中分组展示); P6 解压 1:N 展示与 CLI 待实现。
> 本文件是 P3/P4 共同遵守的契约; 实现顺序见第 8 节。

## 1. 目标与非目标

### 目标

- 压缩前把"哪些条目直接压缩、哪些合并、哪些分包"完整展示给用户审核
- 用户改阈值或勾选后, **只重算方案, 不重新扫描**
- 用户确认后, 实际执行必须与审核过的方案一致(`planId` 校验)
- 审核只读: 用户不能手动拖拽/拆分/合并包成员

### 非目标

- 不预测压缩后大小或精确卷数; 方案只基于原始大小/条目数
- 不展示最终压缩包文件名(随机名/合并包命名在执行阶段才确定)
- 不做手动编辑包成员; 后续如需要, 另立规格
- 不引入传输/校验/重传逻辑

## 2. 默认值与语义

| 参数 | 默认 | 语义 |
|---|---|---|
| 合并阈值 `mergeBelow` | `100m` | `size <= 100m` 进入合并池 |
| 分包阈值 `splitAbove` | `2g` | `size > 2g` 的条目单独分包 |
| 合并包上限 `bundleMax` | 留空 = 跟随 `splitAbove` | 单个合并包原始大小上限 |
| 单包条目上限 `maxEntries` | `50000` | 只约束合并包; 清空 = 不限制 |

- 默认值按二进制单位: `100m` = 100 MiB, `2g` = 2 GiB。若目的地按十进制 2GB 限制, 用户需自行下调; UI 只展示实际生效字节数, 不擅自改用户值。
- 边界: 等于合并阈值 → 合并; 等于分包阈值 → 直接(分包用严格 `>`)。
- 合并包成员数只有 1 个时, 策略会自动退化为"直接压缩", UI 策略列显示"压缩"。
- `maxEntries` 只约束合并包; 单个大目录的条目数超过上限时, UI 可以提示, 但策略无法把它拆开。

## 3. 页面结构

### 3.1 一屏布局

```
┌──────────────────────────────────────────────────────────────┐
│ 压缩 / 解压                                      [确认压缩] │
├──────────────────────────────────────────────────────────────┤
│ 源文件夹 [D:\data]        目标文件夹 [E:\out]                │
├──────────────────────────────────────────────────────────────┤
│ 格式 zip  强度 默认  密码 ...  随机名 □  校验 ☑  排除 ...     │
│ 打包策略  合并≤[100m]  分包>[2g]  合并包≤[跟随]  条目≤[50000] │
│ 预计 12 个压缩包（9 压缩 · 1 分包 · 2 合并）· 最大 1.7GB     │
├──────────────────────────────────────────────────────────────┤
│ ⚠ bigdir 条目数 60000 超过上限 50000, 已改为直接压缩          │
├──────────────────────────────────────────────────────────────┤
│ ☑ 名称                    大小      策略        状态           │
│ ☑ FolderA                 26GB      分包        待处理         │
│ ☑ FolderB                 500MB     压缩        待处理         │
│   合并打包 #1 共 17 个文件  1.7GB     合并        待处理         │
│   fileC                   16KB      —           待处理         │
│   fileD                   20MB      —           待处理         │
│ ...                                                          │
│   未纳入打包 共 1 个文件     —        —           —             │
│ ☐ dirE                    3MB       —           待处理         │
└──────────────────────────────────────────────────────────────┘
```

- 智能打包关闭(默认)或解压模式: 策略行隐藏, 表格是普通文件列表(勾选 / 名称 / 大小 / 状态), 不计算方案。
- 压缩模式勾选「智能打包」后: **同一张表格复用为「打包方案」视图**, 多出一列「策略」; 扫描完成自动计算方案, 方案就绪前先按普通列表显示(策略列占位 `—`), 就绪后切换为按方案分组。
- 摘要常驻策略行内(`#plan-summary`, 随策略行一起显隐); 提醒常驻策略行下方的 `#plan-warnings`, 仅在有提醒时显示, 与表格同屏。
- 摘要中的"最大 1.7GB"指**单条目压缩包或合并包**的原始大小; 分包条目不在其中比较, 否则 26GB 会误导。
- 方案里的一个压缩包不等于一个输出文件: 分包条目可能产生多卷, 实际卷数取决于压缩后大小。

### 3.2 策略行

控件:

| 控件 | id | 说明 |
|---|---|---|
| 合并阈值 | `opt-merge-below` | 文本, 支持 `100m`/`2g`/字节; 空 = 不合并 |
| 分包阈值 | `opt-split` | 文本, 空 = 不分包; 与旧"分包"输入同一语义 |
| 合并包上限 | `opt-bundle-max` | 文本, 空 = 跟随分包阈值 |
| 单包条目上限 | `opt-max-entries` | 数字, 空 = 不限制 |
| 摘要 | `plan-summary` | `aria-live="polite"` |
| 提醒条 | `plan-warnings` | 位于策略行下方; 仅当方案有 warning(如条目数超限)时显示, 无提醒时整条隐藏 |

摘要文案建议:

- 正常: `预计 12 个压缩包（9 压缩 · 1 分包 · 2 合并）· 最大 1.7GB`
- 有分包: 追加 `· 1 个分包按 2GB 切卷`
- 有 warning: 追加 `· 2 条提醒`, 明细同时列在策略行下方的 `#plan-warnings`
- 计算中: `正在计算打包方案…`
- 失败: `方案无效: <错误>`
- 无勾选: `未选择条目`

### 3.3 源表"策略"列

列顺序: 勾选 / 名称 / 大小 / **策略** / 状态。策略列仅在「压缩 + 智能打包」时显示; 普通文件列表没有该列。

| 角色 | 显示 | 说明 |
|---|---|---|
| 压缩包(direct) | 徽章 `压缩` | 单条目, 一包一行 |
| 分包(split) | 徽章 `分包` | 单条目 `size > splitAbove`, 一包一行 |
| 合并标题行(bundle) | 徽章 `合并` | 名称列显示 `合并打包 #N` + 灰色 `共 M 个文件`(M = 该包顶层成员数, 与下方展开的成员行数一致), 大小列是包原始大小合计, 状态列是包级状态; 悬停显示顶层成员数与包内条目数 |
| 合并成员行 | `—` | 名称列行首缩进(`pl-4`), 提示属于上方合并包; 策略列留空; 状态跟随所属包 |
| 未纳入打包(分组标题) | `—` | 表尾分组标题 + 灰色 `共 N 个文件`, 见 3.4 |
| 未勾选条目 | `—` | 不参与方案; 勾选后自动重算 |
| 条目超限 | 琥珀色 `压缩` 徽章 | 合并候选但 `entryCount > maxEntries`, 退化为直接压缩; 悬停说明原因, 同时策略行下方提醒条列出 |

- 悬停 title 显示原因: `26GB > 分包阈值 2GB`、`100MB ≤ 合并阈值 100MB`、`条目数 60000 > 50000, 已改为直接压缩`。
- 合并包标题行悬停 title 显示 `N 项 · M 个条目`; 压缩 / 分包 / 合并单行也各自带原因 tooltip。
- 表格即方案, 不再有抽屉/弹窗, 也没有展开、筛选、关闭等交互; 完整方案直接看表格分组(见 3.4)。

### 3.4 方案表格分组

智能打包且方案就绪时, 条目表格按方案平铺展示(不弹窗、不覆盖):

```
┌ 名称                      大小      策略   状态 ───────────────┐
│ FolderA                   26GB      分包   待处理              │
│ FolderB                   500MB     压缩   待处理              │
│ 合并打包 #1 共 17 个文件    1.7GB     合并   待处理              │
│   fileC                   16KB      —      待处理              │
│   fileD                   20MB      —      待处理              │
│ ...                                                            │
│ 未纳入打包 共 1 个文件       —        —      —                  │
│ dirE                      3MB       —      待处理              │
└────────────────────────────────────────────────────────────────┘
```

分组规则:

- 压缩包 / 分包包各占一行(无标题行); 合并包 = 一行标题「合并打包 #N 共 M 个文件」+ 其成员行。表格严格按 `plan_packages.packages` 的方案顺序平铺(压缩 / 分包单行与合并分组按方案顺序混合出现), 不另做排序。
- 合并包标题行: 标题「合并打包 #N」+ 灰色「共 M 个文件」; M 取该包顶层成员数(`memberIndexes.length`), 即下方展开的成员行数。标题行另有包原始大小合计、策略徽章 `合并` 与包级状态; 悬停显示顶层成员数与包内条目数。
- 合并包成员行: 名称单元格行首缩进(`pl-4`), 视觉上归属上方标题行; 策略列留空(`—`), 状态跟随包。
- 未被勾选的条目集中到表尾「未纳入打包」分组(有未勾选条目时才出现), 标题同样带「共 N 个文件」; 被排除标记的条目默认不勾选, 也落在这个分组, 可手动勾回; 标题行悬停提示未勾选数量, 勾选变化自动重算方案(不重扫)。
- 提醒(条目超限等)显示在策略行下方的 `#plan-warnings`, 与表格同屏; 无提醒时该条隐藏。
- 表格只读审核: 没有拖拽、删除、拆分/合并按钮; 唯一可操作的是勾选框(决定哪些条目参与方案/压缩), 任务运行中勾选框随阈值一起冻结。
- 方案只基于原始大小/条目数: 不显示压缩后大小与实际卷数; 分包行用 tooltip 说明按阈值切卷。

## 4. 交互与状态

### 4.1 触发矩阵

| 变化 | 动作 |
|---|---|
| scan 成功 | 自动调用 `plan_packages` |
| 勾选/取消勾选 | 防抖后重算方案 |
| 合并/分包/合并包/条目阈值变化 | 防抖后重算方案(不重扫) |
| 格式/强度/密码/随机名/校验变化 | 不重算方案 |
| 目标目录变化 | 不重算方案 |
| 排除规则/源目录/模式变化 | 清空方案; 排除规则变化需要重新扫描 |
| 语言切换 | 只重渲染文案, 不重算方案 |

- 方案就绪/更新时直接重绘同一张表格(见 3.4), 不存在抽屉开关状态; 取消勾选「智能打包」立即清空方案并恢复普通文件列表。

### 4.2 计算与失效

- `state.planSeq` 递增; 过期响应丢弃。
- `state.planning = true` 时确认禁用, 但输入不锁(允许继续调阈值)。
- 成功后写入 `state.plan = { planId, packages, summary, warnings }`, 并重建行→包映射; 表格随即切换为方案分组。
- 方案未就绪(计算中/失败/无勾选)时表格先显示普通文件列表(策略列占位 `—`), 确认禁用。
- 失败时 `state.plan = null`, `state.planError = 错误`, 确认禁用; 源表保留。
- 确认时按钮要求: 有勾选 + dst 非空 + plan 存在 + 非 planning + 无 planError。
- 确认请求携带 `planId` 与 packaging 参数; 后端重算并比对, 不一致返回"打包方案已变化, 请重新审核"。

### 4.3 执行状态(包级)

当前"按勾选名单位次推导行状态"不再适用, 改为:

- `state.run.packages`: 按方案顺序的包状态 `pending | running | done | failed`。
- 进度 `done/total` 改按**包**计数; `entry` 为包标签(压缩/分包用条目名, 合并包用 `合并打包 #N`)。
- 行状态 = 其所属包的状态; 合并包的所有成员同步变化; 合并包标题行显示包级状态。
- 包失败: 所有成员行失败; 错误信息挂在成员行状态徽章与状态栏。
- 取消: 已完成包保持完成, 当前包/未开始包回到待处理(半成品由 core 清理)。
- 分包包完成: 所有成员(单条目)完成; 实际卷数不进入行状态。
- 方案在运行期间冻结; 运行中不允许重算/改阈值/改勾选。

## 5. 壳层契约

### 5.1 `plan_packages`

```ts
planPackages({
  src: string,
  entries: string[],              // 勾选名单, scan 原样名字
  packaging: {
    mergeBelow: string | null,    // "100m"
    splitAbove: string | null,    // "2g"
    bundleMax: string | null,     // null = 跟随 splitAbove
    maxEntries: number | null,
  },
}) → PlanResult
```

- 使用壳层缓存的 `ScanReport`, 不读磁盘、不压缩、不占忙锁。
- 名单必须严格匹配; 过期/未知名单返回"扫描结果已过期"。
- 参数由 `parse_size` 解析; 非法返回可读错误。

### 5.2 `PlanResult`

```ts
type PlanResult = {
  planId: string;
  packages: {
    id: string;                   // p0 / p1 ...
    kind: "direct" | "split" | "bundle";
    memberIndexes: number[];      // 指向 scan items, 不重复传名字/大小
    inputBytes: number;
    entryCount: number;
  }[];
  summary: {
    totalPackages: number;
    direct: number;
    split: number;
    bundle: number;
    selectedBytes: number;
    maxDirectOrBundleBytes: number; // 摘要里的"最大"
    maxBundleEntries: number;
    effective: {
      mergeBelow: number | null;
      splitAbove: number | null;
      bundleMax: number | null;
      maxEntries: number | null;
    };
  };
  warnings: {
    code: "tooManyEntries";
    memberIndex: number;
    entryCount: number;
    limit: number;
  }[];
};
```

- `memberIndexes` 避免大方案重复传名字; 内部 `state.rows` 行序 = scan 行序(方案视图只重排渲染, 不改内部行序), 直接映射。
- `planId` = 扫描代数 + 勾选名单(扫描序) + 生效 packaging 参数的稳定哈希。
- 新扫描、改勾选、改阈值都会改变 `planId`。

### 5.3 `compress` 扩展

```ts
compress({
  src, dst, entries,
  options: { ...旧字段, packaging: {...} },
  planId: string,
  onProgress,
}) → {
  cancelled: boolean,
  packages: {
    id: string,
    kind: "direct" | "split" | "bundle",
    archive: string,
    members: string[],
  }[],
  warnings: string[],
}
```

- 后端重新计算方案并比对 `planId`; 不一致在产生任何产物前拒绝。
- `options.packaging` 与 `plan_packages` 参数同构; 旧 `splitSize` 保留为兼容别名。
- `CompressResult.entries` 可保留给旧客户端; 新 UI 使用 `packages`。

## 6. 后端前置(非本文件实现)

- `scan::Entry` 增加 `entry_count`(文件 + 目录; 目录自身计 1), 供 `maxEntries`。
- `strategy` 适配: `Entry → StrategyItem`, 方案成员名解析回 `Entry`。
- 包级压缩: 多源命令(`zip -r out A B C` / `7z a out A B C`), 成员多时 7z 用 `@listfile`; `Bundle` 不切卷, `Split` 切卷。
- 包级 `Report`/`mapping.csv` 1:N; 校验包内根条目与方案成员一致。
- 进度按包计数; 执行顺序 = 方案顺序。
- 解压侧最终支持 1:N mapping 展示(一个包显示多个原名)。

## 7. 验收标准

- 扫描完成自动出现方案摘要; 改阈值/勾选后方案更新且**不触发第二次 scan**。
- 表格按方案分组: 压缩 / 分包各占一行; 合并包以 `合并打包 #N 共 M 个文件` 标题行 + 成员行(行首缩进)展示; 未勾选条目集中在表尾 `未纳入打包` 分组, 可勾回。
- 表格按方案分组展示包类型/成员/原始大小/条目数/警告; 分包不显示假卷数; 提醒条常驻策略行下方且仅在有提醒时显示。
- 摘要的包数与表格分组一致; 最大包口径为压缩/合并包, 分包单独说明。
- 确认时 `planId` 与执行方案一致; 改阈值后旧方案确认被拒。
- 合并包执行时, 所有成员行同步 running/done/failed; 取消回退正确。
- 方案非法/扫描过期时确认禁用并给出可读错误。
- 5 个语言 key 完整; 浏览器预览 mock 也能展示方案。

## 8. 实现顺序

1. P0: 本文件定稿(当前)。
2. P1: `Entry.entry_count` + `strategy` 适配 + 包级计划类型(纯单测)。
3. P2: 包级压缩执行(多源命令/命名/mapping 1:N/Report/进度/校验)。
4. P3: 壳层 `plan_packages` + `planId` + `compress` 扩展。
5. P4: UI 策略行/摘要/策略列/表格分组(先接 mock, 再接 P3)。
6. P5: UI 包级执行状态/取消/失败。
7. P6: 解压 1:N 展示、CLI 参数、i18n、性能与 E2E。

P2 是实际工作量与风险所在; P4 可在 P0/P3 契约上用 mock 数据并行开发。
