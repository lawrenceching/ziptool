# 打包方案审核 UI 规格(P0 契约)

> 定位: P0 设计契约, 供 P3 壳层命令与 P4 UI 实现共同遵守。
> **已拍板**: 审核只读 / 默认开启 100m + 2g / 摘要 + 抽屉。
> 实现进度: P1/P2 core 已完成(2026-10, `Entry.entry_count` + `packaging.rs`); P3 壳层已完成; P4 策略行/摘要/打包列/抽屉与 P5 包级状态已完成; P6 解压 1:N 展示与 CLI 待实现。
> 本文件是 P3/P4 共同遵守的契约; 实现顺序见第 8 节。

## 1. 目标与非目标

### 目标

- 压缩前把"哪些条目直接压缩、哪些合并、哪些分包"完整展示给用户审核
- 用户改阈值或勾选后, **只重算方案, 不重新扫描**
- 用户确认后, 实际执行必须与审核过的方案一致(`planId` 校验)
- 审核只读: 用户不能手动拖拽/拆分/合并包成员

### 非目标

- 不预测压缩后大小或精确卷数; 方案只基于原始大小/条目数
- 不展示最终压缩包文件名(随机名/合并包命名在执行阶段才确定)
- 不做手动编辑包成员; 后续如需要, 另立规格
- 不引入传输/校验/重传逻辑

## 2. 默认值与语义

| 参数 | 默认 | 语义 |
|---|---|---|
| 合并阈值 `mergeBelow` | `100m` | `size <= 100m` 进入合并池 |
| 分包阈值 `splitAbove` | `2g` | `size > 2g` 的条目单独分包 |
| 合并包上限 `bundleMax` | 留空 = 跟随 `splitAbove` | 单个合并包原始大小上限 |
| 单包条目上限 `maxEntries` | `50000` | 只约束合并包; 清空 = 不限制 |

- 默认值按二进制单位: `100m` = 100 MiB, `2g` = 2 GiB。若目的地按十进制 2GB 限制, 用户需自行下调; UI 只展示实际生效字节数, 不擅自改用户值。
- 边界: 等于合并阈值 → 合并; 等于分包阈值 → 直接(分包用严格 `>`)。
- 合并包成员数只有 1 个时, 策略会自动退化为"直接压缩", UI 显示"直接"。
- `maxEntries` 只约束合并包; 单个大目录的条目数超过上限时, UI 可以提示, 但策略无法把它拆开。

## 3. 页面结构

### 3.1 一屏布局

```
┌──────────────────────────────────────────────────────────────┐
│ 压缩 / 解压                                      [确认压缩] │
├──────────────────────────────────────────────────────────────┤
│ 源文件夹 [D:\data]        目标文件夹 [E:\out]                │
├──────────────────────────────────────────────────────────────┤
│ 格式 zip  强度 默认  密码 ...  随机名 □  校验 ☑  排除 ...     │
│ 打包策略  合并≤[100m]  分包>[2g]  合并包≤[跟随]  条目≤[50000] │
│ 预计 12 个逻辑包（9 直接 · 2 合并 · 1 分包）· 最大 1.7GB     │
│ [查看打包方案]                                                │
├──────────────────────────────────────────────────────────────┤
│ ☑ 名称        大小      打包        状态                     │
│ ☑ FolderA     26GB      分包        待处理                   │
│ ☑ FolderB     100MB     合并 #1     待处理                   │
│ ☑ fileC       16KB      合并 #1     待处理                   │
│ ...                                                          │
└──────────────────────────────────────────────────────────────┘
```

- 策略行在压缩模式**且「智能打包」勾选时**显示; 解压模式或未勾选时隐藏(不勾选 = 不计算方案, 每个顶层条目单独压缩, `compress` 传 `packaging=null` 且无 `planId`)。
- 摘要始终可见(位于策略行内, 随策略行一起显隐), 即使抽屉关闭。
- 摘要中的"最大 1.7GB"指**直接包或合并包**的原始大小; 分包条目不在其中比较, 否则 26GB 会误导。
- "逻辑包"不等于输出文件数: 分包条目可能产生多卷, 实际卷数取决于压缩后大小。

### 3.2 策略行

控件:

| 控件 | id | 说明 |
|---|---|---|
| 合并阈值 | `opt-merge-below` | 文本, 支持 `100m`/`2g`/字节; 空 = 不合并 |
| 分包阈值 | `opt-split` | 文本, 空 = 不分包; 与旧"分包"输入同一语义 |
| 合并包上限 | `opt-bundle-max` | 文本, 空 = 跟随分包阈值 |
| 单包条目上限 | `opt-max-entries` | 数字, 空 = 不限制 |
| 摘要 | `plan-summary` | `aria-live="polite"` |
| 查看方案 | `plan-open` | 打开抽屉; 方案计算中/失败时禁用 |

摘要文案建议:

- 正常: `预计 12 个逻辑包（9 直接 · 2 合并 · 1 分包）· 最大 1.7GB`
- 有分包: 追加 `· 1 个分包按 2GB 切卷`
- 有 warning: 追加 `· 2 条提醒`(琥珀色)
- 计算中: `正在计算打包方案…`
- 失败: `方案无效: <错误>`
- 无勾选: `未选择条目`

### 3.3 源表"打包"列

列顺序: 勾选 / 名称 / 大小 / **打包** / 状态。

| 状态 | 显示 | 说明 |
|---|---|---|
| 直接 | `直接` | 单条目, 未超过分包阈值且未进入合并池 |
| 分包 | `分包` | 单条目 `size > splitAbove` |
| 合并 | `合并 #N` | 进入第 N 个合并包 |
| 未选 | `—` | 未勾选, 不参与方案 |
| 排除 | `排除` | 被排除标记且未手动勾选 |
| 条目超限 | `直接 · 超限` | 合并候选但 `entryCount > maxEntries`, 退化为直接; 琥珀色 |

- 悬停 title 显示原因: `26GB > 分包阈值 2GB`、`100MB <= 合并阈值 100MB`、`条目数 60000 > 50000, 已改为直接压缩`。
- 行与方案抽屉双向高亮: 点行内包徽章 → 打开抽屉并定位; 点抽屉成员 → 高亮/滚动到源表行。

### 3.4 方案抽屉

用 `<div role="dialog" aria-modal="true">` 覆盖层(不用 `<dialog>`, 便于 jsdom 测试与焦点控制)。

```
┌─ 打包方案 ───────────────────────────────────────── [关闭] ┐
│ 当前策略：合并≤100MB · 分包>2GB · 合并包≤2GB · 条目≤50k   │
│ [全部 12] [直接 9] [合并 2] [分包 1]                       │
│                                                            │
│ ┌ 合并 #1   1.7GB · 17 项 · 3.4 万文件 ─────────────────┐ │
│ │ FolderB 100MB   fileE 100MB   folderF 20MB ...        │ │
│ │ [展开全部]                                             │ │
│ └────────────────────────────────────────────────────────┘ │
│ ┌ 分包   FolderA 26GB · 单条目 > 2GB ───────────────────┐ │
│ │ 压缩时按 2GB 切卷；实际卷数取决于压缩后大小            │ │
│ └────────────────────────────────────────────────────────┘ │
│ ⚠ bigdir 条目数 60000 > 50000，已改为直接压缩              │
│ 注：大小为原始大小；压缩后大小/实际卷数未知。              │
└────────────────────────────────────────────────────────────┘
```

卡片规则:

- 头部: 类型徽章 + `合并 #N`/`直接`/`分包` + 原始总大小 + 顶层成员数 + 包内条目数。
- 成员默认显示前 20 个; `展开全部` 逐步渲染, 不一次性铺 5 万行。
- 分包卡片不列卷, 只说明"按上阈值切卷; 实际卷数取决于压缩后大小"。
- 合并卡片显示成员 + 大小; 目录成员附条目数 tooltip。
- 抽屉 footer 固定提示"大小为原始大小; 压缩后未知", 避免误解。
- 警告放列表顶部; 过滤 tab 上显示计数。
- 抽屉只读: 没有拖拽、删除、拆分按钮。

## 4. 交互与状态

### 4.1 触发矩阵

| 变化 | 动作 |
|---|---|
| scan 成功 | 自动调用 `plan_packages` |
| 勾选/取消勾选 | 防抖后重算方案 |
| 合并/分包/合并包/条目阈值变化 | 防抖后重算方案(不重扫) |
| 格式/强度/密码/随机名/校验变化 | 不重算方案 |
| 目标目录变化 | 不重算方案 |
| 排除规则/源目录/模式变化 | 清空方案; 排除规则变化需要重新扫描 |
| 语言切换 | 只重渲染文案, 不重算方案 |

### 4.2 计算与失效

- `state.planSeq` 递增; 过期响应丢弃。
- `state.planning = true` 时确认禁用, 但输入不锁(允许继续调阈值)。
- 成功后写入 `state.plan = { planId, packages, summary, warnings }`, 并重建行→包映射。
- 失败时 `state.plan = null`, `state.planError = 错误`, 确认禁用; 源表保留。
- 确认时按钮要求: 有勾选 + dst 非空 + plan 存在 + 非 planning + 无 planError。
- 确认请求携带 `planId` 与 packaging 参数; 后端重算并比对, 不一致返回"打包方案已变化, 请重新审核"。

### 4.3 执行状态(包级)

当前"按勾选名单位次推导行状态"不再适用, 改为:

- `state.run.packages`: 按方案顺序的包状态 `pending | running | done | failed`。
- 进度 `done/total` 改按**包**计数; `entry` 为包标签(直接/分包用条目名, 合并包用 `合并 #N`)。
- 行状态 = 其所属包的状态; 合并包的所有成员同步变化。
- 包失败: 所有成员行失败; 错误信息挂在包徽章与状态栏。
- 取消: 已完成包保持完成, 当前包/未开始包回到待处理(半成品由 core 清理)。
- 分包包完成: 所有成员(单条目)完成; 实际卷数不进入行状态。
- 方案在运行期间冻结; 运行中不允许重算/改阈值/改勾选。

## 5. 壳层契约

### 5.1 `plan_packages`

```ts
planPackages({
  src: string,
  entries: string[],              // 勾选名单, scan 原样名字
  packaging: {
    mergeBelow: string | null,    // "100m"
    splitAbove: string | null,    // "2g"
    bundleMax: string | null,     // null = 跟随 splitAbove
    maxEntries: number | null,
  },
}) → PlanResult
```

- 使用壳层缓存的 `ScanReport`, 不读磁盘、不压缩、不占忙锁。
- 名单必须严格匹配; 过期/未知名单返回"扫描结果已过期"。
- 参数由 `parse_size` 解析; 非法返回可读错误。

### 5.2 `PlanResult`

```ts
type PlanResult = {
  planId: string;
  packages: {
    id: string;                   // p0 / p1 ...
    kind: "direct" | "split" | "bundle";
    memberIndexes: number[];      // 指向 scan items, 不重复传名字/大小
    inputBytes: number;
    entryCount: number;
  }[];
  summary: {
    totalPackages: number;
    direct: number;
    split: number;
    bundle: number;
    selectedBytes: number;
    maxDirectOrBundleBytes: number; // 摘要里的"最大"
    maxBundleEntries: number;
    effective: {
      mergeBelow: number | null;
      splitAbove: number | null;
      bundleMax: number | null;
      maxEntries: number | null;
    };
  };
  warnings: {
    code: "tooManyEntries";
    memberIndex: number;
    entryCount: number;
    limit: number;
  }[];
};
```

- `memberIndexes` 避免大方案重复传名字; UI 行序 = scan 行序, 直接映射。
- `planId` = 扫描代数 + 勾选名单(扫描序) + 生效 packaging 参数的稳定哈希。
- 新扫描、改勾选、改阈值都会改变 `planId`。

### 5.3 `compress` 扩展

```ts
compress({
  src, dst, entries,
  options: { ...旧字段, packaging: {...} },
  planId: string,
  onProgress,
}) → {
  cancelled: boolean,
  packages: {
    id: string,
    kind: "direct" | "split" | "bundle",
    archive: string,
    members: string[],
  }[],
  warnings: string[],
}
```

- 后端重新计算方案并比对 `planId`; 不一致在产生任何产物前拒绝。
- `options.packaging` 与 `plan_packages` 参数同构; 旧 `splitSize` 保留为兼容别名。
- `CompressResult.entries` 可保留给旧客户端; 新 UI 使用 `packages`。

## 6. 后端前置(非本文件实现)

- `scan::Entry` 增加 `entry_count`(文件 + 目录; 目录自身计 1), 供 `maxEntries`。
- `strategy` 适配: `Entry → StrategyItem`, 方案成员名解析回 `Entry`。
- 包级压缩: 多源命令(`zip -r out A B C` / `7z a out A B C`), 成员多时 7z 用 `@listfile`; `Bundle` 不切卷, `Split` 切卷。
- 包级 `Report`/`mapping.csv` 1:N; 校验包内根条目与方案成员一致。
- 进度按包计数; 执行顺序 = 方案顺序。
- 解压侧最终支持 1:N mapping 展示(一个包显示多个原名)。

## 7. 验收标准

- 扫描完成自动出现方案摘要; 改阈值/勾选后方案更新且**不触发第二次 scan**。
- 源表每行有打包归属; 合并包所有成员显示同一个 `合并 #N`。
- 抽屉可查看包类型/成员/原始大小/条目数/警告; 分包不显示假卷数。
- 摘要的包数与抽屉/源表一致; 最大包口径为直接/合并包, 分包单独说明。
- 确认时 `planId` 与执行方案一致; 改阈值后旧方案确认被拒。
- 合并包执行时, 所有成员行同步 running/done/failed; 取消回退正确。
- 方案非法/扫描过期时确认禁用并给出可读错误。
- 5 个语言 key 完整; 浏览器预览 mock 也能展示方案。

## 8. 实现顺序

1. P0: 本文件定稿(当前)。
2. P1: `Entry.entry_count` + `strategy` 适配 + 包级计划类型(纯单测)。
3. P2: 包级压缩执行(多源命令/命名/mapping 1:N/Report/进度/校验)。
4. P3: 壳层 `plan_packages` + `planId` + `compress` 扩展。
5. P4: UI 策略行/摘要/打包列/抽屉(先接 mock, 再接 P3)。
6. P5: UI 包级执行状态/取消/失败。
7. P6: 解压 1:N 展示、CLI 参数、i18n、性能与 E2E。

P2 是实际工作量与风险所在; P4 可在 P0/P3 契约上用 mock 数据并行开发。
